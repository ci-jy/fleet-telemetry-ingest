# fleet-telemetry-ingest

Vehicles send GPS and ignition messages over MQTT, and this service turns them into trips: where each vehicle went, how far, and how long it sat idling. Every point is kept in PostgreSQL, and the trips can be browsed through a REST API and a small React page. The harder half was keeping the counts right when an ingest pod, the broker or the database gets killed in the middle of a stream.

## Running it

You need Node.js 20 or newer and Docker with the compose plugin.

```bash
npm ci
npm run build
docker compose up -d --wait   # Mosquitto on 127.0.0.1:21883, Postgres on 127.0.0.1:25432
npm start                     # API + web page on http://127.0.0.1:23000
```

To get some data in, publish a seeded fake fleet. With `--check` it compares the trips the service found against the simulator's ground truth:

```bash
npm run sim -- --seed 42 --devices 20 --trips 4 --check
```

Then open http://127.0.0.1:23000 and click through devices, trips and tracks. Settings are environment variables, listed in [docs/configuration.md](docs/configuration.md) along with the API endpoints and the message format.

`npm test` runs the unit and integration tests without Docker, using PGlite (Postgres compiled to WASM) and an in-process MQTT broker. The tests run in GitHub Actions on every push ([.github/workflows/ci.yml](.github/workflows/ci.yml)), followed by a Docker fault-injection suite. Details are in [docs/testing.md](docs/testing.md).

There's also a Kubernetes version. With k3d, Helm and kubectl installed:

```bash
bash scripts/k8s-e2e.sh --quick
```

That builds a k3d cluster, installs the Helm chart and replays a 200-vehicle fleet four times, once per fault: deleting ingest pods, scaling the StatefulSet up and down, and restarting the broker and the database. It writes `reports/k8s-chaos.json`. This is the last run:

## How it works

Each message has a device id and a sequence number that only goes up, and that pair is the primary key of the points table. If the broker delivers something twice, the insert hits `ON CONFLICT DO NOTHING` and the trip code never sees the copy. So I could use ordinary QoS 1 MQTT with a persistent session and not worry about redeliveries.

Messages are written in small batches, one transaction each. A buffer per device puts them back into sequence order, waiting up to 30 s of device time for a missing one. After that a state machine decides whether the vehicle is parked, moving or idling, and opens and closes trips. Its output depends only on the points it gets, in order. When the service starts it replays the stored points for each device and ends up where it left off, with no separate state file.

Acknowledgements were harder than I expected. By default mqtt.js acks a QoS 1 message to the broker as soon as my handler receives it, before anything is in the database. I hold the ack back until the batch commits. If the process dies in between, the broker still has the message and sends it again.

With several pods, devices are hashed into 16 partitions, each with its own MQTT session. A pod owns a partition through a lease row in Postgres, and the row's token goes up on every handover. Each batch checks the lease before writing. If another pod has taken over, the batch is refused and the broker redelivers those messages to the new owner.

The state machine table and the recovery rules are in [docs/design.md](docs/design.md). Load tests and trip accuracy against the simulator are in [PERFORMANCE.md](PERFORMANCE.md).

## Known issues and next steps

- When GPS drops out, the distance across the gap is a straight line between the points on either side, so curvy roads come out short. There's no map matching.
- mqtt.js has no public way to delay the ack, so I wrap its internal `_sendPacket`. That's a private method, and I'd have to check it again after any mqtt.js upgrade.
- The partition count is fixed. Changing `PARTITIONS` moves devices to other partitions and needs a full drain and restart. Pods also split partitions evenly by count, not by how busy they are.
- The k3d suite runs one seed and one fault at a time. Next I'd like to run several seeds in CI and combine faults, for example killing a pod while the broker restarts.
