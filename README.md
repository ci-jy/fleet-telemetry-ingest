# fleet-telemetry-ingest

Vehicles send GPS and ignition messages over MQTT, and this service turns them into trips (where each vehicle went, how far, how long it sat idling) that you can browse through a REST API and a small React page. The harder half was keeping the counts right when an ingest pod, the broker or the database gets killed mid-stream. In the last Kubernetes run, across four faults (pod kills, scaling, broker and database restarts), 236,809 distinct messages were stored with 0 lost and 0 duplicated.

## Running it

You need Node.js 20 or newer and Docker with the compose plugin.

```bash
npm ci
npm run build
docker compose up -d --wait   # Mosquitto on 127.0.0.1:21883, Postgres on 127.0.0.1:25432
npm start                     # API + web page on http://127.0.0.1:23000
```

To get some data in, publish a seeded fake fleet. With `--check` it compares the trips the service found against the simulator's ground truth:

```bash
npm run sim -- --seed 42 --devices 20 --trips 4 --check
```

Then open http://127.0.0.1:23000 and click through devices, trips and tracks. Settings, API endpoints and the message format are in [docs/configuration.md](docs/configuration.md).

`npm test` runs the tests without Docker, against PGlite (Postgres in WASM) and an in-process MQTT broker. CI also runs a Docker fault-injection suite, see [docs/testing.md](docs/testing.md).

For the Kubernetes version you need k3d, Helm and kubectl:

```bash
bash scripts/k8s-e2e.sh --quick
```

That builds a k3d cluster, installs the Helm chart, replays a 200-vehicle fleet once per fault and writes `reports/k8s-chaos.json`. This is the last run:

## How it works

Each message carries a device id and a sequence number that only goes up, and that pair is the primary key of the points table in PostgreSQL. A redelivered message hits `ON CONFLICT DO NOTHING` and the trip code never sees it. So plain QoS 1 MQTT with a persistent session is enough.

Messages are written in small batches, one transaction each. A buffer per device puts them back in sequence order, waiting up to 30 s of device time for a missing one, and a state machine marks the vehicle parked, moving or idling and opens and closes trips. Its output depends only on the points, so at startup the service just replays them and ends up where it left off.

Acknowledgements were harder than I expected. By default mqtt.js acks a QoS 1 message as soon as my handler receives it, before anything is in the database. I hold the ack back until the batch commits. If the process dies in between, the broker still has the message and sends it again.

With several pods, devices are hashed into 16 partitions, each with its own MQTT session. A pod owns a partition through a lease row in Postgres whose token goes up on every handover. If another pod has taken over, the old owner's next batch is refused and the broker redelivers those messages to the new one.

The state machine and recovery rules are in [docs/design.md](docs/design.md), and load tests and trip accuracy in [PERFORMANCE.md](PERFORMANCE.md).

## Known issues and next steps

- When GPS drops out, the distance across the gap is a straight line, so curvy roads come out short. There's no map matching.
- mqtt.js has no public way to delay the ack, so I wrap its private `_sendPacket`, which I'd have to recheck after any upgrade.
- The partition count is fixed. Changing `PARTITIONS` moves devices between partitions and needs a full drain and restart.
